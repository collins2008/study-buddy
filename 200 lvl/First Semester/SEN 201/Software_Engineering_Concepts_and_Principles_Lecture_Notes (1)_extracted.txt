SOFTWARE ENGINEERING CONCEPTS AND PRINCIPLES

1. Introduction to Software Engineering

Software Engineering is a systematic, disciplined, and measurable approach to the
development, operation, maintenance, and evolution of software systems. It applies
engineering principles, methods, tools, and processes to produce software that satisfies
user requirements, meets quality standards, remains maintainable, and is delivered
within agreed time and budget constraints.

Software Engineering extends beyond programming. Programming focuses primarily
on writing instructions that a computer can execute, while Software Engineering
encompasses the entire software life cycle, including requirements analysis, design,
implementation, testing, deployment, maintenance, project management, and quality
assurance.

1.1 Definition of software
Software is a collection of computer programs, procedures, configuration data, and
associated documentation that enables a computer system to perform specific tasks.

i. Operating systems such as Windows and Linux.
ii. Web applications such as online banking platforms.
iii. Mobile applications such as electronic payment applications.
iv. Enterprise systems such as university management systems.
v. Embedded software in medical equipment, vehicles, and industrial control systems.

1.2 Why Software Engineering is important
i. Managing complexity: large applications contain many interconnected components

that must work together.

ii. Improving software quality: engineering methods reduce defects and improve

reliability, usability, security, and performance.

iii. Controlling development costs: planning, estimation, and early defect detection

reduce unnecessary expenditure.

iv. Meeting user requirements: requirements engineering helps ensure that software

addresses actual user needs.

v. Supporting maintenance: well-structured software is easier to modify, repair, and

extend.

vi. Enhancing security: secure development practices help identify and mitigate

vulnerabilities.

vii.

Promoting teamwork: defined roles, standards, and documentation improve

collaboration.

viii. Ensuring timely delivery: project planning and iterative development help teams

manage schedules and changing priorities.

2. Fundamental Software Engineering Concepts

2.1 Software product
A software product consists of executable software and supporting materials needed to
use, operate, configure, and maintain it.

i. Generic products: developed for a broad market, such as accounting applications or

word processors.

ii. Customized products: developed for a particular customer or organization, such as a

university's internal attendance management system.

2.2 Software process
A software process is a structured set of activities used to develop and maintain
software. Major activities include software specification, design and implementation,
validation, and evolution. These activities may be repeated in iterative development.

2.3 Software requirements
Requirements describe the services a system must provide and the constraints under
which it must operate.

Functional requirements describe what
the system should do. Examples for a
university attendance management system include allowing lecturers to log in,
recording attendance, and generating reports.

Non-functional requirements specify qualities or constraints. Examples include a
defined response-time target, restricted access to attendance records, an agreed
availability target, and compatibility with approved browsers and devices.

2.5 Software design
Software design transforms requirements into a technical plan for implementation. It
defines modules, interfaces, data structures, algorithms, and interactions. A good
design should be understandable, modular, testable, secure, and adaptable to change.

2.6 Software testing
i. Unit testing: tests an individual function, class, or module.
ii. Integration testing: tests interactions between components.
iii. System testing: evaluates the complete integrated application.
iv. Acceptance testing: determines whether software meets user or business acceptance

criteria.

2.7 Software maintenance
Software maintenance involves modifying software after delivery to correct faults,
adapt to environmental changes, improve performance, or prevent future problems.

3.2 Modularity
Modularity divides a system into smaller, manageable,
relatively independent
components. A student system might contain registration, course management,
examinations, fee payment, and reporting modules.

3.3 Encapsulation and information hiding
Encapsulation combines data and operations in a unit such as a class. Information
hiding restricts access to internal details and exposes controlled operations. In a bank-
account class, balance changes should occur through validated methods rather than
unrestricted direct modification.

3.4 Separation of concerns
Different responsibilities should be handled independently. A university portal should
separate interface presentation, authentication, academic business rules, database
operations, and monitoring.

3.5 High cohesion
Cohesion describes how closely related the responsibilities within a module are. A
GradeCalculator module that calculates grades has high cohesion; adding email, user
management, and payment functions would weaken its focus.

3.6 Low coupling
Coupling measures dependency between modules. Low coupling means modules
communicate through clear, stable interfaces and depend as little as practical on one
another's internal details.

3.7 Reusability
Reusable components can be applied in multiple contexts without unnecessary
rebuilding. Examples include authentication services, validation functions, logging
libraries, and shared APIs.

3.8 Simplicity
Software should be as simple as reasonably possible while meeting requirements.
Unnecessary complexity increases defects and maintenance effort. Simplicity does not
justify ignoring security, reliability, or scalability needs.

3.9 Don't Repeat Yourself (DRY)
Avoid unnecessary duplication of knowledge or business rules. Centralizing course-
registration eligibility rules reduces inconsistent updates. Similar-looking code should
not be combined prematurely if the responsibilities may evolve independently.

3.10 Single Responsibility Principle (SRP)
A module or class should have one coherent responsibility and one principal reason to
change. For example, invoice calculation, invoice storage, and email notification can
be separate responsibilities.

3.11 Open–Closed Principle (OCP)
Software components should be open for extension but closed for modification. A
payment system can support new providers through a shared interface without
repeatedly rewriting stable registration logic.

3.12 Dependency Inversion Principle (DIP)
High-level business logic should depend on abstractions rather
than concrete
implementation details. A registration service can depend on a PaymentGateway
interface instead of being tied to one provider.

3.13 Principle of least privilege
Each user, process, or component should receive only the permissions required for its
duties. Students, lecturers, administrators, and technical staff should have appropriately
limited access.

3.14 Defensive programming
Anticipate invalid inputs, unexpected states, and operational failures. Validate input,
handle connection failures, reject unauthorized requests, and avoid unsafe assumptions
about external data.

3.15 Continuous improvement
Review processes using evidence such as defect rates, test results, user feedback,
delivery performance, and maintenance effort. Use the findings
to improve
development practices.

4.1 Planning and feasibility study
i. Technical feasibility: are the required technologies and skills available?
ii. Economic feasibility: do expected benefits justify costs?
iii. Operational feasibility: can the organization operate and support the system?
iv. Schedule feasibility: can the project be completed within the required time?

Example: Before developing an online attendance platform, a university should

student privacy, and system support.

4.2 Requirements analysis

document analysis, prototyping, and use-case development.

4.3 System design
System design covers architectural design, database and data-structure design, user-
interface design, component and class design, API specifications, security, and error
handling.

4.4 Implementation
Implementation translates designs into executable code. Good practices include coding
standards, version control, code reviews, automated tests, documenting important
decisions, and managing dependencies.

4.5 Testing, deployment, and maintenance
Testing should be planned throughout development. Deployment may involve
configuration, database migration,
training, monitoring, backups, and
installation,

and user expectations change.

5.1 Waterfall model
The Waterfall model organizes development

Advantages: clear stages and deliverables; straightforward progress tracking; useful
when requirements are stable. Disadvantages: late changes can be costly, working

5.2 Prototyping model
A prototype is an early representation used to clarify requirements or evaluate design
alternatives. The team builds a prototype, gathers feedback, refines requirements, and
develops the production system. A key risk is that a quick prototype may be mistaken
for production-ready software despite inadequate security, architecture, performance,
or error handling.

6. Requirements Engineering
Requirements Engineering is the systematic process of discovering, analyzing,
documenting, validating, and managing software requirements. Poor requirements can
lead to technically functional systems that fail to solve the intended problem.

6.1 Activities in requirements engineering
i. Elicitation: collect information from stakeholders.
ii. Analysis: identify conflicts, dependencies, ambiguities, and priorities.
iii. Specification: document agreed requirements.
iv. Validation: confirm that requirements reflect stakeholder needs.
v. Management: track and control changes throughout the project.

6.2 Stakeholder identification
Stakeholders influence, use, fund, operate, or are affected by software. For a university
attendance system, they may include students, lecturers, level advisers, administrators,
Heads of Department, university management,
IT support, and data-protection
personnel.

6.3 Use cases
A use case describes how an actor interacts with a system to achieve a goal. Example:
a lecturer authenticates, selects an authorized course, opens a session, records
attendance, and saves the records. A precondition is that the lecturer is authorized to
manage the course; a postcondition is that valid records are stored and available for
authorized reporting.

6.4 User stories
A user story often follows this format: “As a [type of user], I want [a capability], so
that [a benefit].” Example: “As a lecturer, I want to view attendance percentages for
my course so that I can identify students who may need academic support.”
Acceptance criteria should make completion verifiable.

7. Software Design Principles and Design Methods

7.1 Top-down design
Top-down design begins with the overall system and progressively decomposes it into
subsystems and modules. A library system might be decomposed into book
management, member management, and loan management,
then into search,
registration, lending, and return functions. It provides an overall view but can spread
the effects of incorrect assumptions.

7.2 Bottom-up design
Bottom-up design begins with reusable low-level components and combines them into
higher-level subsystems. Components might include database access, authentication
utilities, validation, and logging. It encourages independent testing but can produce
components that do not fit the architecture if requirements are poorly understood. Both
approaches are often combined.

7.3 Functional decomposition
Functional decomposition divides a system into functions and subfunctions. A payroll
system may contain employee-data processing, salary calculation, tax computation,
deductions, payment processing, and payslip generation. Excessive decomposition can
produce too many small functions with complicated dependencies.

7.4 Object-oriented design
Object-oriented design organizes software around objects that combine state and
behavior. Four commonly taught concepts are encapsulation, abstraction, inheritance,
and polymorphism.

Python example:

class Notification:

def send(self, message):

raise NotImplementedError

class EmailNotification(Notification):

def send(self, message):

print("Email:", message)

class SMSNotification(Notification):

def send(self, message):

def notify_user(service, message):

service.send(message)

notify_user(EmailNotification(), "Registration completed")
notify_user(SMSNotification(), "Registration completed")

This illustrates polymorphism and allows additional notification types to be introduced.

9. Software Testing and Verification
Software testing evaluates software behavior and identifies defects under selected
conditions. Testing provides evidence of quality but cannot prove the absence of every
possible defect.

9.1 Verification and validation
Verification asks: “Are we building the product according to its specified requirements
and design?” Examples include reviews,
technical
specifications.

inspections, and tests against

Validation asks: “Are we building a product that meets users' actual needs and
intended purpose?” Examples include acceptance testing, usability evaluation, and
operational trials. Both are necessary.

9.2 Testing approaches
i. Black-box testing: tests externally observable behavior without relying on internal

code structure.

ii. White-box testing: uses knowledge of internal code, logic, branches, and execution

paths.

iii. Grey-box testing: combines external behavior testing with partial knowledge of

internal implementation.

9.3 Functional and non-functional testing
Functional testing checks whether features behave according to requirements. Non-
functional testing examines performance, usability, security, accessibility, reliability,
and compatibility.

9.6 Test-driven development
i. Write a test describing desired behavior.
ii. Run the test and observe it fail.
iii. Implement the minimum code needed to pass.
iv. Refactor the code while preserving passing tests.
Test-driven development encourages testable design and rapid feedback but does not
replace system, acceptance, security, or performance testing.

9.7 Continuous integration
Continuous integration frequently integrates changes into a shared codebase and
automatically runs checks such as builds, unit tests, and static analysis. It helps identify
integration problems early.

10.3 Cost and effort estimation
Estimation predicts the resources required to complete a project. Methods include
expert judgment, analogy with previous projects, parametric models, decomposition,
and historical productivity data.

Example: if a team estimates 120 person-days of work and plans for three full-time
developers, a simplified effort-based duration is 120 person-days ÷ 3 persons = 40
working days. Actual delivery may take longer because of coordination, dependencies,
leave, rework, and tasks that cannot be parallelized.

10.4 Risk management
involves identifying risks, assessing likelihood and impact,
Risk management
prioritizing them, planning responses, and monitoring changes. Examples include loss
of a key developer, changing requirements, security vulnerabilities, vendor failure,
data migration errors, and delayed approvals.

10.5 Version control
Version control tracks changes to source code and project files. Git is widely used for
distributed version control, while hosting platforms support collaboration, pull requests,
issue tracking, and code review. Good practices include meaningful commits,
descriptive branches, peer review, protected main branches, and never committing
passwords or secret keys.

10.6 Configuration management
Software configuration management identifies and controls changes to source code,
dependencies, build settings, infrastructure definitions, and release configurations. It
supports reproducible builds, traceability, controlled releases, and rollback.

11.1 Refactoring
Refactoring improves the internal structure of existing code without intentionally
changing externally observable behavior. Examples include extracting repeated logic,
simplifying conditional statements, and separating unrelated responsibilities. Tests
help prevent unintended behavior changes.

11.2 Technical debt
Technical debt is the future cost associated with design or implementation shortcuts,
outdated dependencies, inadequate testing, or other decisions that make changes harder.
A technical-debt register can record the issue, impact, proposed remedy, and priority.

12. Software Engineering Ethics and Professional Responsibilities

12.1 Privacy and confidentiality
Collect, access, use, retain, and disclose personal data only for legitimate and
authorized purposes. Follow applicable data-protection obligations and implement
suitable safeguards.

12.2 Security responsibility
Consider security throughout the life cycle. Practices include threat modeling, secure
coding, access control, dependency management, vulnerability remediation, and
incident response.

12.3 Honesty and transparency
Report defects, limitations, risks, and test results accurately. Do not misrepresent
system capabilities or claim tests were performed when they were not.

12.4 Professional competence
Work within one's competence, seek expert guidance when necessary, and continually
develop technical knowledge.

13. Practical Case Study: University Attendance Management System

13.1 Problem statement
A university currently records student attendance manually. The process consumes
lecture time, makes it difficult to calculate attendance percentages, and may allow
inaccurate records. The university intends to develop a
duplicate entries or
computerized attendance management system.

13.2 Project objectives
i. Reduce time required to record attendance.
ii. Improve accuracy and consistency of attendance records.
iii. Allow authorized lecturers to access course attendance lists.
iv. Generate attendance summaries and reports.
v. Protect student records against unauthorized access and modification.

13.3 Requirements specification
Functional requirements: authenticate users; maintain student and course records;
allow authorized lecturers to open attendance sessions; record and update attendance
according to approved rules; and generate reports for authorized users.

Non-functional requirements: enforce role-based access control; protect sensitive
information in transit and at rest as appropriate; define measurable response-time and
availability targets; maintain audit trails for important changes; and support backup
and recovery.

15. Emerging Trends in Software Engineering

15.1 Artificial intelligence-assisted software development
AI tools can support code generation, explanation, test creation, documentation, and
defect analysis. AI-generated code must be reviewed and tested because it may contain
incorrect logic, insecure practices, licensing concerns, or fabricated APIs. Developers
remain responsible for the quality and suitability of the result.

15.4 DevSecOps
DevSecOps integrates security into development and operations. Examples include
automated dependency scanning, secret detection, security testing in CI/CD pipelines,
infrastructure checks, and continuous vulnerability management.

15.6 Green software engineering
Green software engineering considers environmental effects of software operation and
development. Practices include reducing unnecessary computation, improving resource
utilization, optimizing data transfer, selecting efficient algorithms, and monitoring
energy and infrastructure costs.
